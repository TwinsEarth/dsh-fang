# PM 主动开票策略（v3.1.25）

> 目的：让「大模型主动开票」真正生效。决策中心链路一直是通的，但 PM 从不调用
> `ask_user_choice` / `request_human_decision`，于是「开发一整天也看不到一张票」。
>
> 策略落在两处（因为模型只能看到第二处）：
> 1. 本文件（人读）；
> 2. **工具 description**（模型读）——由 `src/plugins/decision-center.mjs` 的
>    `PM_DECISION_POLICY` / `PM_PROACTIVE_HINT` 注入，改策略就改那里。

## 一、必须开票（mustAsk）

| # | 情形 |
|---|---|
| 1 | 要在两个及以上合理方案里做取舍（架构 / 技术选型 / 交互形态），且代价不可忽略 |
| 2 | 要执行不可逆或难以回滚的动作：删除数据、重置分支、强制推送、覆盖生产配置、发版 |
| 3 | 要触碰凭据、权限、外部账号、付费资源或对外承诺 |
| 4 | 需求存在歧义或缺失关键信息，不同理解会导致返工 |
| 5 | 要越过既定范围（改用户没要求的模块、扩大 mandate、跨仓库操作） |
| 6 | 发现阻塞缺陷但修复方案会改变对外行为 / 契约 |
| 7 | 长时间任务（>10 分钟）需要中途改变方向 |

## 二、不要开票（mustNotAsk）

- 低风险、可回滚、在既定范围内的实现细节（命名、注释、内部结构、测试补全）；
- 等价于「继续」的常规推进，以及取文件 / 跑测试 / 格式化这类机械操作；
- 已经有明确约定的既定方案（此前已确认过）。

> 判据：开票的成本是「打断一个人的注意力」，只有**决策代价 > 打断代价**时才开票。

## 三、提问规则（rules）

1. 一次只问一个决定点，问题要具体到「选哪个」或「能不能做」；
2. 必须给 2–4 个可执行选项，推荐项放第一个并把标签后缀 `(推荐)`；
3. `context` 写清：为什么需要人决定、每个选项的代价与风险、不决定的后果；
4. `red` 用于**阻塞**（人不在就没法继续）；`yellow` / `blue` 用于「记录并继续」，不要滥用 red；
5. **绝对不要因为「不确定」而把问题原样抛回给开发者** —— 先把能自己查的查清。

## 四、AI 自动决策的边界（autoDecide）

| 项 | 默认 | 说明 |
|---|---|---|
| `autoDecide.enabled` | `true` | 关闭后所有票都必须人工回答 |
| `autoDecide.levels` | `["green"]` | 只对低注意力票自动决策 |
| `autoDecide.minConfidence` | `0.8` | 建议置信度下限 |
| `autoDecide.allowUnknownRisk` | `false` | 推荐项风险未知时是否允许自动 |

**硬红线**：`red` 与任何 `isBlocking` 的票**永不自动决策**，必须人工显式选择。
自动决策会写 `resolvedBy: "ai-auto"` 并记审计 `decision-ai-auto-resolved`。

## 五、如何验证策略生效

```bash
# 1) 工具描述里应能看到策略（模型读得到）
node -e "import('./src/plugins/decision-center.mjs').then(m=>console.log(m.PM_DECISION_POLICY.mustAsk.length))"

# 2) 运行态：让 PM 遇到一个必然需要人决定的问题，观察是否出现新票
curl -H "x-fang-auth: <token>" http://127.0.0.1:<port>/fang/api/decisions

# 3) 收件箱：0 条时应看到常驻入口（半透明 + 计数 0）
```
